# ViewTransition InvalidStateError investigation

Branch: `feature/immersive-hero-poc`. Local changes only; no merge or deployment.

## Confirmed cause and evidence

The error is a browser-managed **cross-document View Transition** rejection, triggered by the optional `@view-transition { navigation: auto; }` enrollment in `src/components/features/editorial/film.css`. Both the portfolio and case studies imported that stylesheet. This feature preceded the Milestone 3C modal; the modal uses GSAP and same-document history, with no View Transitions API calls.

Reproduced in Chromium 156.0.8078.4 against the existing Next.js 16.3.8 development server:

- `artifacts/view-transition/baseline-dev.json`: exact `InvalidStateError` on browser Back from a case study to the gallery entry. The outgoing case-study document emitted `unhandledrejection`; Playwright also received `pageerror` with an empty JavaScript stack. The probe observed no `document.startViewTransition` calls. Incoming `pagereveal` carried a native transition.
- `artifacts/view-transition/baseline-nonintrusive-dev.json`: reproduced the exact rejection during a real case-study “Back to Projects” link to `/#works`. This second probe did **not** inspect transition objects or wrap `document.startViewTransition`, ruling out those diagnostics as the cause.
- Initial load, gallery open/close, and gallery-only history steps did not produce the rejection in those runs.
- Simple isolated HTML-only navigation did not reproduce it in either development or the previous static export. Therefore this was not universal to every navigation; do not infer a production-wide failure or blame React lifecycle from the screenshot alone.
- After removing enrollment, the same full nonintrusive development probe produced no errors: `artifacts/view-transition/after-nonintrusive-dev.json`.

The exact message is generated by Chromium's `kOptInDisabled` branch, which rejects an incoming cross-document transition when the opt-in is disabled/missing. See the [Chromium implementation and reason enum](https://chromium.googlesource.com/chromium/src/+/bed98a9780b75372c1974d8aa0e48f1433082e2f%5E%21/). [Chrome's documentation](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document) confirms that CSS opt-in alone starts cross-document transitions, without a `document.startViewTransition` call.

No Next.js experimental view-transition configuration was enabled, and no application `startViewTransition` caller was found. Next development tooling mirrored the browser rejection into its development log; that log is not evidence that Next created the rejected promise. The precise stylesheet/activation timing that caused Chrome to see a disabled opt-in was not independently isolated. The native transition path and the controllable CSS trigger were confirmed; removing that optional feature removes the failing path instead of catching or hiding its errors.

## Focused fix and changed files

- `src/components/features/editorial/film.css`: remove native cross-document enrollment, native transition pseudo-element animations/keyframes, and the shared-image styling override. Existing carousel/card CSS transitions and reduced-motion rules remain.
- `src/components/features/editorial/FilmReel.tsx`: remove imperative shared-image transition names and their cleanup; retain real anchors, session frame persistence, and pageshow detail reset.
- `src/app/work/[slug]/page.tsx`: remove the matching shared-image transition name and unused type import; preserve image object positioning and route content.
- `tests/navigation-console.spec.mjs`: add normal/reduced-motion browser flows observing `pageerror`, console errors, and `unhandledrejection` across document navigation. The listeners never call `preventDefault`, catch transition promises, or replace browser APIs. Warnings remain visible and are recorded separately.
- `tests/film-reel.spec.mjs`: update the obsolete expectation that native transitions must occur. Its focused HTML navigation test uses the existing constrained-device fallback, while the new console test covers the live WebGL journey.
- This report.

No changes were made in this investigation to gallery GSAP timelines, camera paths, scroll restoration, focus management, router configuration, billboard visuals, dependencies, or dependency internals. Case-study links now perform ordinary document navigation without the optional browser shared-image/page fade; the cinematic gallery fade remains intact.

## THREE.Clock warning

Application source has no Clock constructor. The exact constructor is in the installed `@react-three/fiber` **9.8.2**, `dist/events-e51d7528.esm.js:1207`:

```js
clock: new THREE.Clock(),
```

It initializes Fiber's root store. The equivalent development/production CommonJS bundles contain the same constructor at line 1232. Three.js **0.186.1** emits the warning from `src/core/Clock.js:61`, deprecated since r183.

The baseline CDP console stack independently confirms `Three.Clock → Fiber store initializer → createStore → createRoot → CanvasImpl` (see `baseline-dev.json`, first `warning-stack` entry). This is a dependency-owned API, not an application clock. The warning is retained and reported; no internal patch, console filter, clock replacement, or version upgrade was applied.
